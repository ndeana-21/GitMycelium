# Производительность на огромных монорепозиториях

Цель: репозиторий порядка **1 000 000 коммитов и нескольких тысяч веток**
открывается за секунды, скроллится без фризов, а операции не блокируют UI.

## Референсы (проверенные)

- **gitui** на репе Linux git (`900k+` коммитов): парсинг **24 с**, **0.17 ГБ** RAM,
  без фризов; lazygit — 57 с / 2.6 ГБ; tig — 4 м 20 с / 1.3 ГБ. Планка на 900k+
  коммитов достижима и для C++/libgit2, но 24 с на полную историю — всё равно
  много для «open repo», поэтому обязателен lazy-подход.

## Стратегия

### 1. Ничего не читать целиком

- Первый экран = HEAD-страница (первые N коммитов) + статус. Рисуем мгновенно.
- История подгружается страницами (revwalk окнами), раскладка графа — по мере
  поступления, в фоне.
- Полный обход commit-graph — только для операций, которым он реально нужен
  (поиск, статистика), и тоже в фоне с прогрессом.
- Жёсткий потолок визуализации с настройкой (аналог Max Commits), но по умолчанию
  «видимая область + буфер» через виртуализацию `ScrollArea::show_rows`.

### 2. Git-фичи для больших реп (прозрачно, по кнопке «Оптимизировать»)

- **commit-graph** (`git commit-graph write --reachable --changed-paths`) —
  ускоряет обход и `--changed-paths` помогает diff/логам.
- **multi-pack-index** (`git multi-pack-index write`) — быстрый доступ к объектам
  в куче паков.
- **partial clone / promisor** (`clone --filter=blob:none`, при необходимости
  `--filter=tree:0` + `--sparse`) — блобы тянутся по требованию. Проверено по
  git-scm partial-clone: клиент описывает ненужные объекты, сервер их опускает,
  клиент корректно обрабатывает отсутствующие и дозагружает. **Мы обязаны это
  поддерживать — libgit2 из коробки не умеет.**
- **sparse-checkout (cone)** — большие рабочие деревья без полного чекаута.
- **fsmonitor + notify** — быстрая инвалидация status.
- **Фоновое обслуживание**: `git maintenance start` (gc, commit-graph,
  prefetch), опционально.

### read-path (C++/libgit2)

- Read-path — **libgit2** (C API), парсинг паков/индекса/commit-graph без запуска
  процессов.
- Батчинг CLI там, где нужен именно git: `git for-each-ref --format=…` одним
  вызовом, `git ls-files -u -z`, `git status --porcelain=v2 -z`. Никаких N+1
  вызовов на ветку/файл.
- Кэш разобранных объектов (LRU) между панелями и страницами.
- `GIT_OPTIONAL_LOCKS=0`, `LC_ALL=C`, `-c core.quotepath=false`,
  `-c diff.renames=copies` по необходимости.
- **Promisor-репы** (`extensions.partialClone` / `.promisor`): libgit2 их не
  откроет — переключаемся на CLI (`git cat-file`, `git log`, `git fetch`).

### 4. Отзывчивость UI (Qt)

- GUI-поток не делает git. Тяжёлое — `RepoSession` + `QThreadPool`.
- Модели Qt инкрементальны: `canFetchMore`/`fetchMore` для истории,
  страничные `dataChanged`-апдейты для diff/status.
- Отменяемые операции: `QProcess` kill, флаг отмены в акторе.
- Прогресс-индикаторы для fetch/gc/maintenance (парсим stderr git).

### 5. Большие диффы и файлы

- Diff считается лениво: по файлу, по странице, по ханкам.
- **`src/diff`**: line-diff делегирован libgit2 (алгоритм xdiff) — проверенный и
  быстрый; свой слой отвечает за ханки/word-diff и отображение. Ограничение
  размера, «diff truncated, показать всё» для гигантских файлов; бинарники — по
  флагу `GIT_DIFF_FLAG_BINARY`.
- Синтаксическая подсветка — инкрементально, только видимые строки
  (`QSyntaxHighlighter` / tree-sitter вне GUI-потока, с кэшем).

### 6. Метрики приёмки (бенчмарк-набор)

Гонять на трёх репах: (1) синтетическая 1M коммитов; (2) реальная монорепа уровня
Linux/Chromium; (3) репа пользователя. Целевые:
- open repo до первого кадра: **< 1 с**;
- скролл графа: **60 fps**, без фризов;
- переключение коммита: **< 100 мс** до появления diff;
- status на репе 100k файлов: **< 300 мс** (fsmonitor);
- merge-редактор открывается: **< 200 мс** для файла ≤ 10k строк.

Бенчмарки держим в репо (`criterion`), регрессии ловим в CI.

## Известные ловушки

- libgit2 не умеет partial clone — если репа promisor, читать её через libgit2
  нельзя (ругается на отсутствующие объекты). Поэтому read-path для таких реп —
  CLI.
- libgit2 потокобезопасен на уровне библиотеки, но не допускает параллельных
  операций над одним репозиторием → actor на репу.
- Electron-урок: не тащить всё состояние в UI-модель целиком; на 1M коммитов
  модель должна быть страничной (`canFetchMore`/`fetchMore`).

## Замеры (бенчмарк, I-3)

`bench/gitmycelium-bench <repo> [pages] [page-size]` замеряет чтения, которыми
открывается окно. `scripts/make-big-repo.sh <dir> [commits] [branches] [files]`
строит синтетическую репу через `git fast-import` (100k коммитов / 1000 веток —
~5 с, ~48 МБ). Тайминги в ctest не гоняются: бенчмарк, который утверждает, — это
флейки-тест.

Синтетика 100k коммитов, 991 ветка, 20 200 загруженных строк (AllRefs):

| замер | было | стало |
|:--|--:|--:|
| open + первая страница | 312 мс | 312 мс |
| ещё 100 страниц (пагинация) | 7168 мс | 18 мс |
| раскладка графа, один shot (20k строк) | 238 мс | 155 мс |
| раскладка графа, append 100 страниц | 6832 мс | 143 мс |
| худшая страница раскладки | 162 мс | 2 мс |
| refs / refs-by-commit / status | 4 / 4 / 1 мс | 4 / 4 / 1 мс |

Первая страница на 100k укладывается в цель «open < 1 с». Находка бенчмарка:
`Repository::commits()` пересоздавал revwalk на каждую страницу (push всех refs +
топологическая сортировка), поэтому пагинация была квадратичной — 72 мс/страница
и росла с глубиной. Теперь обход кэшируется между страницами и сбрасывается,
когда ref/HEAD может сдвинуться (`invalidateCommitWalk`, из `guarded`/`recorded`
и из `refreshPanels`); пагинация стала линейной.

Второй замер — `GraphLayout::append` — вскрыл ту же болезнь в раскладке: каждая
страница пересчитывала весь загруженный диапазон (O(rows × lanes)). Теперь `append`
продолжает проход с состояния дорожек, оставленного прошлой страницей, и считает
только новые строки; порядок дорожек по важности (`updateLaneOrder`) переставляется
целиком только когда он для уже нарисованных дорожек изменился, иначе — только для
новых строк. `setCommits`/`setTipColors`/`setTipPriority` по-прежнему пересчитывают
всё: это решения уровня refresh, не страницы. Тест
`incrementalPagesMatchOneShotOnAWideGraph` сравнивает оба пути поле в поле.

## Замеры на 1M коммитов (обход по commit-graph, раскладка с общими наборами дорожек)

Синтетика `make-big-repo.sh … 1000000 3000 2000` (1M коммитов, 2995 веток, в первых
20 200 строках живут 2218 дорожек) и блоблесс-клон git/git (85 517 коммитов, 197 дорожек).
Обе колонки — Release-сборка одного и того же бенчмарка (`build-rel/bench/gitmycelium-bench
<repo> 100 200`); Debug медленнее в 4–5 раз и для замеров не годится.

| замер | 1M: было | 1M: стало | git/git: было | git/git: стало |
|:--|--:|--:|--:|--:|
| open + первая страница | 3403 мс | 133 мс | 523 мс | 20 мс |
| ещё 100 страниц | 20 мс | 73 мс | 41 мс | 158 мс |
| раскладка графа, 20k строк | 399 мс | 47 мс | 49 мс | 26 мс |
| пик памяти процесса | 2,37 ГБ | 270 МБ | 334 МБ | 182 МБ |

Первая страница — это обход: libgit2 с любой сортировкой разбирает всю историю до первого
коммита, а `git/topo_walk` — алгоритм самого git (`--topo-order`), которому commit-graph даёт
номера поколений и потому глубину обхода по требованию. Цена — следующие страницы: обход
досчитывает глубину по мере прокрутки, а коммиты страницы читаются из pack, а не из кэша,
который старый обход заполнял целиком; 0,7–1,6 мс на страницу.

Без commit-graph обход полный, как и у git: 3,4 с и ~0,9 ГБ на 1M. Поэтому интерактивное
окно, прочитав вне графа 10 000+ коммитов, один раз пишет его в фоне (`git commit-graph write
--reachable --split`, 3,6 с на 1M, следующий слой — десятки миллисекунд).

Память раскладки: наборы живых дорожек над и под строкой теперь общие у всех строк, где набор
не изменился (`LaneSet`); копия на строку давала rows × lanes — 2,3 ГБ на 20 000 строках.
